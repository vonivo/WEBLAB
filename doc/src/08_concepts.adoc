== Querschnittliche Konzepte

=== Datenmodell
Das Datenmodell besteht aus insgesamt 3 MonogDB-Collections:

* User
* Team
* Game

[plantuml, data-model, svg]
----

sind keine eigenständigen Entitäten und werden im MongoDB-Dokument eingebettet.

=== Authentication
Die Anmeldung erfolgt passwortlos mit WebAuthn (Passkeys) und liefert ein JWT.
Geschützte Funktionen (z.B. das Erstellen eines Teams) erfordern ein gültiges JWT.

*Backend*

* Das Login/Register wird über den `WebAuthnController` mittels `@simplewebauthn/server` realisiert. Nach erfolgreichem Login wird ein JWT generiert und ausgeliefert.
* Für die Implementation der JWT-Funktionalität wird `@nestjs/jwt` verwendet.
* Die Klasse `AuthGuard` kann verwendet werden, um Ressourcen zu schützen.

*Frontend*

* Nach erfolgreichem Login/Register wird der `AuthService` aufgerufen, welcher das JWT im LocalStorage des Browsers speichert.
* Bei jedem HTTP-Request wird über den `authInterceptor` das JWT an den Request angefügt.
* `AuthService` stellt dem Rest der Applikation den Login-Status des Benutzers zur Verfügung.

=== Validierung
*Backend*

Input-Validierung auf der Seite des Backends wird mittels einer `global ValidationPipe` mit class-validatorDTOs realisiert.
Weitergehende Business-Validation-Rules werden von den einzelnen Service-Klassen ausgeführt.

*Frontend*

Die Validierung im Frontend wird mithilfe der in Signal-Forms eingebauten Validierungsmechanismen umgesetzt.

=== Teststrategie

Getestet wird auf drei Ebenen.

[cols="1,3,2"]
|===
|Ebene |Gegenstand |Werkzeug

|Unit-Tests Frontend
|Komponenten, Services und Route Guards. Dumb Components werden isoliert über Inputs und Outputs getestet, Services mit gemockten Abhängigkeiten.
|Vitest (`ng test`)

|Unit-Tests Backend
|Services und Auth Guard. Abhängigkeiten werden über Dependency Injection ersetzt.
|Vitest, `@nestjs/testing`

|Integration-Tests Backend
|Die REST-API wird über Integrations mithilfe einer In-Memory MongoDB integrativ getestet.
|Vitest, `@nestjs/testing`

|End-to-End-Tests
|Kritische Abläufe über das gesamte System: Anmelden, Spiel und Ereignisse erfassen, Teams verwalten.
|Cypress gegen die Umgebung aus `docker-compose.e2e.yml`
|===

Bei jedem Push prüft die CI (GitHub Actions) für Frontend und Backend die Formatierung
(Prettier), buildet das Backend und Frontend und führt die Unit-Tests aus.
Die End-to-End-Tests werden manuell gestartet.
