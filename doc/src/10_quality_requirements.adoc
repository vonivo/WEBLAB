== Qualitätsanforderungen
=== Übersicht der Qualitätsanforderungen
Die wichtigsten Qualitätsziele sind in Kapitel 1.2 beschrieben (Desktop und
Mobile, Performance, Erweiterbarkeit, Reproduzierbarkeit). Die folgende
Übersicht ergänzt sie um weitere Anforderungen.

[cols="1,3,1"]
|===
|Qualitätsmerkmal |Anforderung |Priorität

|Benutzbarkeit
|Die Oberfläche ist auf Desktop und Mobile bedienbar.
|hoch (Kap. 1.2)

|Performance
|Das Prod-Bundle erreicht im Lighthouse-Score durchschnittlich mindestens 90.
|hoch (Kap. 1.2)

|Erweiterbarkeit
|Neue Funktionen lassen sich ergänzen, ohne bestehende Bereiche umzubauen.
|hoch (Kap. 1.2)

|Reproduzierbarkeit
|Die Anwendung ist mit einem Befehl startbar.
|hoch (Kap. 1.2)

|Sicherheit
|Nur angemeldete Benutzer dürfen Daten ändern, es werden keine Passwörter gespeichert.
|mittel

|Datenkonsistenz
|Vergangene Spiele bleiben korrekt, auch wenn Teams später geändert werden.
|mittel

|Zuverlässigkeit der Eingaben
|Ungültige Eingaben werden abgelehnt und nicht gespeichert.
|mittel

|Wartbarkeit und Testbarkeit
|Änderungen werden automatisch geprüft, die Komponenten sind einzeln testbar.
|mittel

|Internationalisierung
|Weitere Sprachen lassen sich einfach hinzufügen.
|niedrig

|Aktualität
|Neue Ereignisse erscheinen ohne manuelles Neuladen.
|mittel (noch nicht erfüllt)
|===

=== Qualitätsszenarien

[cols="1,1,3,3"]
|===
|ID |Merkmal |Szenario |Erwartetes Resultat

|Q1
|Benutzbarkeit
|Ein Benutzer öffnet das Spiel auf dem Smartphone und ein Admin erfasst ein Ereignis auf dem Desktop. Beide können die Aufgabe ohne Einschränkung erledigen.
|Auf beiden Geräten sind Inhalte und Bedienelemente ohne horizontales Scrollen oder Zoomen nutzbar.

|Q2
|Performance
|Ein Benutzer öffnet die Anwendung mit einer 3G Verbindung.
|Das Prod-Bundle erreicht im durchschnittlichen Lighthouse-Score mindestens 90.

|Q3
|Erweiterbarkeit
|Der Betreiber möchte ein neues Feature ergänzen (z. B. Saisons).
|Änderungen betreffen im Wesentlichen einen neuen Feature-Ordner im Frontend und ein Modul im Backend.

|Q4
|Reproduzierbarkeit
|Ein Dozent möchte die Anwendung starten.
|Die Anwendung ist mittels `docker compose up --build` startbar. Danach ist sie unter `http://localhost` erreichbar.

|Q5
|Sicherheit
|Ein nicht angemeldeter Benutzer versucht, ein Spiel oder Team zu ändern.
|Das Backend lehnt die Anfrage mit `401` ab.

|Q6
|Datenkonsistenz
|Ein Team wird nach einem Spiel umbenannt oder gelöscht.
|Das vergangene Spiel zeigt weiterhin den ursprünglichen Namen und die ursprüngliche Aufstellung.

|Q7
|Zuverlässigkeit der Eingaben
|Ein Admin erfasst ein Spiel mit zwei gleichen Teams oder ein Tor ohne Spieler.
|Das Backend lehnt die Anfrage ab und speichert nichts.

|Q8
|Wartbarkeit
|Ein Entwickler pusht eine Änderung.
|Formatierung, Build und Unit-Tests laufen automatisch und melden Fehler innerhalb der CI.

|Q9
|Internationalisierung
|Es soll eine weitere Sprache angeboten werden.
|Dafür genügt eine zusätzliche Übersetzungsdatei.

|Q10
|Aktualität
|Ein Admin erfasst ein Tor.
|Ein Benutzer sieht es innerhalb von 5 Sekunden, ohne die Seite neu zu laden.
|===
